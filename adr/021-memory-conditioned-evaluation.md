# ADR: Memory-conditioned evaluation separates retrieval from generation

- Status: Accepted
- Date: 2026-08-13
- Last reviewed: 2026-08-13

## Context

Step 13 answers the project's research question for the current checkpoint: does retrieved
memory help? The generation backend is now Aira Core, but the model is (at best)
smoke-trained, so it cannot reproduce facts. A naive "did the model output the fact?"
metric would read ~0 everywhere and hide the fact that retrieval *is* delivering the
right context. The evaluation plan also forbids an LLM judge and requires honest,
non-cherry-picked reporting.

## Decision

1. **Two metrics, kept apart.** For each task the evaluator measures **context
   availability** — did the expected fact reach the backend's context? (a retrieval
   property) — and **generation adherence** — did the model reproduce it? (a generation
   property). Separating them makes it possible to attribute outcomes to the retriever or
   the generator rather than conflating them.
2. **Three baselines.** no-memory (empty context), Aira Memory (retrieved + ranked +
   budgeted context) and full-history (all active memories concatenated). Context cost and
   latency are reported per baseline, so Aira's safe delimited framing vs naive
   concatenation is visible.
3. **Real stack, Core as backend.** Setup turns run through the actual capture pipeline;
   the query is generated by `TinyTransformerBackend`. Memory never imports torch — the
   backend is wired only through the `GenerationBackend` protocol.
4. **Honest conclusion, generated from the numbers.** The report states plainly when
   retrieval helps context while the untrained checkpoint does not reproduce facts, and
   labels generation-side benefit inconclusive at this scale — a training limitation, not a
   retrieval one. No result is cherry-picked and no frontier comparison is made.
5. **Versions and ablation recorded.** The report records the model parameter count,
   config dimensions, checkpoint (or none) and seed, and includes a small ranking ablation
   (default vs lexical-only) on context availability.
6. **Deterministic and reproducible.** Fixed clock, CPU greedy generation and a seeded
   model make the report's `canonical()` view byte-stable across runs.

## Alternatives considered

- Report only generation adherence. Rejected: it would read ~0 and misleadingly suggest
  memory does not help, hiding the retrieval contribution.
- Train the model enough to copy from context before evaluating. Rejected for this step:
  it would conflate Step 12's training scope and risk overstating results; the honest
  answer for the current checkpoint is the deliverable.
- An LLM judge for adherence. Rejected by the evaluation plan; substring checks on known
  facts are deterministic.

## Consequences

- The repository contains a reproducible experiment: on the built-in tasks, Aira Memory
  raises context availability from 0.0 (no memory) to 1.0, while generation adherence is
  0.0 for the untrained checkpoint and forgotten facts are never disclosed. The finding is
  reported without overstatement.
- Because the model is untrained, generation-side numbers are not evidence about the
  memory system's quality; they are evidence about model scale/training, and are labelled
  as such.

## Traceability

- Requirements: connect `TinyTransformerBackend` to chat without coupling memory to
  PyTorch; controlled tasks; three baselines; factual/correction/forgetting metrics;
  context cost + latency; separate retriever vs generator failures; record versions;
  report negatives honestly; ranking ablation.
- Upholds invariants: 2/9 (forgotten non-disclosure), 12 (measured, reproducible), and the
  two-system boundary.
- Realized in stage 13; release hardening (Step 14) re-runs the gates.

## Migration path

When a meaningfully trained checkpoint exists, re-run `aira memeval --checkpoint …`; the
same harness will then report generation adherence that is interpretable. Add tasks and
bump the report schema as the task set grows.
